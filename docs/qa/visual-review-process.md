# Visual review — the one way a visual change is approved

Owner's rule (Gabor, 2026-11-18): **every visual change is reviewed on the same kind of page, in every session and on
every machine** — his Mac, Vera's Mac, a cloud session. The page is generated by code, the answers come back as text
in a fixed format, and a script decides what the answers allow. No session improvises its own review, and no baseline
is re-recorded from a "looks fine" in chat.

The pixel gate (`npm run test:visual`) only proves "looks like before". This process is how a person says "the new
look is right".

## The loop

```bash
npm run build && npm run test:visual        # 1. red run: test-results/ now holds expected / actual / diff per screen
npm run visual:page                         # 2. → .visual-review/  (add  -- --spec docs/qa/reviews/<date>-<topic>.json)
#                                             3. publish the page (below), give the owner the link, stop and wait
npm run visual:page -- --answers answers.txt   # 4. the owner's pasted text, saved to a file → what is allowed now
npm run test:visual:update -- --approved-by="<owner's name>" --note="<what changed>"   # 5. only if step 4 allows it
```

1. **Run the suite against a fresh production build.** A green run needs no review.
2. **Generate the page.** `scripts/visual-review-page.ts` reads every snapshot that differs from its baseline and writes
   `.visual-review/` (git-ignored): `index.html` (the page), `local.html` (the same page as a complete document),
   `img/` (JPEG copies), `files.json` (the file list for publishing) and `review.json` (what was asked, with the build
   fingerprint).
3. **Publish it and ask.**
   - **Claude with the Artifact tool** (desktop app, claude.ai): publish `.visual-review/index.html` with
     `root: ".visual-review"` and `files:` the array in `.visual-review/files.json`. In a later round of the same
     review, publish to the same artifact (`url`), so the owner keeps one link. The artifact is private to its owner.
   - **No Artifact tool:** serve the folder and open `/local.html` (in the Claude app: the launch entry `visual-review-page` in `.claude/launch.json` does exactly this) —
     `./node_modules/.bin/vite preview --outDir .visual-review --port 4175`. A `file://` page does not load its pictures
     in the app's browser pane.
   - Then give the link, say in two lines what changed, and **end the turn**. Do not re-record, do not commit.
4. **Read the answers with the script, not by eye.** The owner presses *Copy answers* and pastes the text. Save it to a
   file and run `--answers`. It prints every *Issue* with its note, every decision's pick, and one verdict:
   - **may re-record** only if every screen under review is `OK`, `BASELINES` is `YES`, and the `Build:` line of the
     answers equals the fingerprint of the pictures on disk (the owner approved exactly these pixels);
   - **may commit** only if, in addition, `COMMIT` is `GO`.
   - Anything else — an `Issue`, an unanswered screen, `NO`, answers for another build — is **not approved**: fix, run
     the suite, generate the next round (`"round": n + 1` in the spec), ask again.
5. **Re-record through the approval script only**, with the owner's name. It logs the change in
   `docs/qa/visual-baselines-log.md`. Then run the suite once more: it must be green.

## The spec file (optional, one per review, committed)

`docs/qa/reviews/<date>-<topic>.json` gives the page its context. Every field is optional.

| Field | Meaning |
|---|---|
| `title`, `round`, `intro` | Page name (keep it the same in every round), round number, two or three plain sentences for the owner |
| `screens` | `{ "<snapshot id>": ["what changed", …] }` — shown on that screen's card. Write what a person sees, not CSS |
| `approved` | Snapshot ids that still differ from the baseline but were marked OK in an earlier round **and have not changed since**: listed, not asked again |
| `decisions` | Taste or copy choices: `{ id, title, text, options: [{ id, label, images: ["path.png"], recommended }] }`. Pictures are paths from the repo root; produce them by rendering the option, never by describing it |
| `ownerSteps` | Things only the owner can do (a test mail, a dashboard click) |
| `lang` | `"en"` (default) or `"hu"`: the page's own wording. In Hungarian the screens are marked *Rendben* / *Javítandó* and the two closing questions read "Megfelel így az új megjelenés?" and "Elmenthetem a változtatást?". The pasted answer format is identical in both languages, so `--answers` reads either |
| `goLive` | `true` for a content release of the CMS Coordinator: the second closing question means "publish to the website" ("Közzétehetem az oldalon?") and its GO is what `npm run release:publish-content` requires. Default `false` (commit and push the branch) |

The page always ends with the same two questions, `BASELINES` (YES / NO) and `COMMIT` (GO / WAIT). They are part of
the answer format; do not rename them.

## Rules

- **Pre-screen before you ask.** Look at every picture yourself first (`diff` shows where). The owner's pass confirms;
  it should not be the one that finds a cut-off photo or a mid-word break.
- **One screen, one verdict.** If a screen changes after it was marked OK, it goes back into `screens` in the next
  round — remove it from `approved`.
- **An `Issue` note is an instruction, not a hint.** Do what it says, or ask one question if it can be read two ways.
  Then show the result again.
- **Decisions are shown as pictures of the real page with the option applied** (a style override in a throw-away
  browser context is enough). Mark your suggestion; the owner may pick against it; record the pick, do not re-argue.
- **Never re-record to make a red run green**, never widen a threshold, never use sample answers you typed yourself to
  test the script as if they were the owner's.
- The page shows the site's own screenshots and nothing else. Do not put keys, mail addresses of customers or inbox
  content on it.

## What the page looks like (so every round is recognisable)

Linen background, the brand's Cormorant headings. Part 1: one card per screen with *Before / After / Difference*, the
list of changes, *OK / Issue* and a note field. Part 2: decisions with picture options, then the two closing
questions. Part 3 (if any): what only the owner can do. A bar at the bottom counts open answers and holds
*Copy answers*. Marks are remembered in the browser per build, so a reload does not lose them.

First used: site polish, 2026-11-16 to 2026-11-18 (`docs/qa/reviews/2026-11-18-site-polish.json`); rounds one and two
of that review were hand-built and are the model this script reproduces.
